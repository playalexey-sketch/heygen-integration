# 03 · Задание для OpenClaw

Документ написан как **готовый бриф-промпт**. Его можно целиком отдать агенту
(`openclaw agent --agent builder --message-file docs/clawdesk/03-OPENCLAW-BRIEF.md`)
или использовать как ТЗ для команды. Разделы 1–3 — контекст и правила, раздел 4 —
пошаговые задания, раздел 5 — критерии приёмки.

---

## 1. Роль и цель

Ты — ведущий инженер проекта **ClawDesk**. Нужно построить продукт-аналог Grok Bot
на базе OpenClaw: мессенджер, где контакты — это боты-сотрудники с собственным
изолированным компьютером, памятью, доступами к рабочим сервисам и правом действовать
самостоятельно до момента, когда требуется подпись человека.

Полный контекст: `docs/clawdesk/00-STRATEGY.md`, `01-ARCHITECTURE.md`, `02-FUNCTIONALITY.md`.
Заготовки конфигов и скиллов: `docs/clawdesk/examples/`.

Цель первой итерации — пройти демо-сценарий из раздела «Скоуп MVP» файла `02-FUNCTIONALITY.md`
без ручных правок кода между шагами.

## 2. Жёсткие правила

1. **Не форкать ядро OpenClaw.** Всё делать плагинами, скиллами, конфигом и внешним BFF.
   Если чего-то не хватает в апстриме — оформить issue/PR в апстрим, а у себя сделать
   временный адаптер в `packages/gateway-client`, изолировав обходной путь в одном месте.
2. **Gateway — источник правды.** Не дублировать транскрипты, сессии и роутинг.
   BFF ходит в gateway по WS-протоколу и CLI, а не в его файлы состояния напрямую.
3. **Один бот = один контейнер = один браузерный профиль = один набор секретов.**
   Нарушать нельзя ни ради скорости, ни ради удобства демо.
4. **Секреты никогда не попадают в контекст модели.** Только SecretRef и подстановка
   на уровне рантайма. В аудите — редакция.
5. **Никаких polling-циклов** для ожидания sub-агентов. Только `sessions_yield`
   и push-completion, как требует OpenClaw.
6. **Необратимое действие без аппрува невозможно.** Отсутствие политики трактуется
   как «требуется аппрув», а не как «разрешено».
7. **Нет артефакта проверки — нет статуса `done`.**
8. **Автологин по паролям запрещён.** Только ручной первичный вход человеком,
   капча/2FA → остановка и эскалация.
9. Каждая задача из раздела 4 завершается рабочим кодом, тестом и записью в `CHANGELOG.md`.
10. Язык интерфейса и документации — русский; код, идентификаторы, коммиты — английский.

## 3. Технические рамки

- Node 26, TypeScript strict, pnpm workspaces, Fastify, React + Vite, Tauri для десктопа.
- Postgres 16 + Drizzle, Redis + BullMQ, S3-совместимое хранилище (MinIO локально).
- Docker/Podman для sandbox ботов. Playwright для детерминированных шагов браузера.
- Схемы — TypeBox/Zod, валидация на границах. Тесты — vitest + playwright.
- Структура репозитория — как в `01-ARCHITECTURE.md`, раздел 3.

## 4. Задания

### Задание 1 · Базовый стек и gateway

**Что сделать**

1. Поднять монорепозиторий `pnpm` со структурой `apps/{bff,web,desktop}`,
   `packages/{gateway-client,bot-spec,routine-spec,policy,ui-kit}`,
   `plugins/{clawdesk-bridge,clawdesk-recorder}`, `skills/clawdesk-core`, `infra/`.
2. `infra/docker-compose.yml`: openclaw-gateway, postgres, redis, minio, bff, web.
   Gateway биндить на `0.0.0.0` внутри сети compose, наружу — только через BFF.
3. `packages/gateway-client`: типизированный WS-клиент протокола gateway —
   `connect` (с device identity и подписью challenge), `req/res`, подписка на события
   `agent`, `chat`, `presence`, `health`, идемпотентные ключи для `send`/`agent`,
   реконнект с backoff, восстановление подписок.
4. Управление конфигом gateway: чтение/запись `openclaw.json` через API конфига,
   валидация схемой, версионирование файла в git-репозитории состояния,
   hot-reload и откат при ошибке валидации.

**Готово, когда:** `docker compose up` поднимает стек; BFF подключается к gateway,
логирует `hello-ok`; интеграционный тест отправляет agent run и получает ответ.

### Задание 2 · Реестр ботов и провижининг

**Что сделать**

1. `packages/bot-spec`: схема `BotSpec` (см. `01-ARCHITECTURE.md`, 3.1) + компилятор
   `BotSpec → { agentEntry, bindings, identityMd, agentsMd, toolPolicy, sandboxConfig }`.
2. Профили инструментов `reader / operator / engineer / dispatcher` как пресеты
   `tools.allow/deny` (таблица в 3.1). Пресет — данные, не код.
3. Provisioner в BFF:
   - создание workspace `~/.clawdesk/workspaces/<botId>` с `IDENTITY.md`, `AGENTS.md`, `GOALS.md`
     (шаблоны в `examples/`);
   - запись `agents.entries.<botId>` и `bindings[]` в конфиг gateway;
   - создание docker-контейнера `clawdesk/bot-runtime` с меткой `clawdesk.bot=<botId>`,
     томами `workspace` и `chrome-profile`, лимитами cpu/mem, без privileged, без docker.sock;
   - выделение отдельного CDP-порта и отдельного Chrome-профиля;
   - egress-allowlist (iptables/NetworkPolicy) по списку сервисов бота.
4. Idle-freeze: воркер паузит контейнер после 10 минут без активности, будит по запросу
   за < 3 с; состояние томов сохраняется.
5. Увольнение бота: остановка контейнера, отзыв секретов, архивация workspace,
   удаление bindings, сохранение аудита.
6. REST + WS API: `POST /bots`, `GET /bots`, `PATCH /bots/:id`, `DELETE /bots/:id`,
   `POST /bots/:id/wake`.

**Готово, когда:** созданы два бота, каждый в своём контейнере со своим Chrome-профилем;
залогинены в один сервис под разными аккаунтами; куки не пересекаются (тест проверяет
изоляцию через сравнение cookie jar); после паузы и пробуждения сессии живы.

### Задание 3 · Мессенджер

**Что сделать**

1. `apps/web`: интерфейс мессенджера — сайдбар со штатом и каналами, окно чата,
   треды, композер, вложения, markdown/код, поиск. Компоненты в `packages/ui-kit`.
2. Треды-задачи: тред отображает план, шаги с иконками статуса, прогресс, стоимость,
   артефакты, свёрнутый лог действий.
3. Инлайн-карточка аппрува с кнопками **Одобрить / Изменить / Отклонить** и
   переключателем «не спрашивать до $X».
4. «Показать работу»: модальное окно с таймлайном скриншотов и подписями шагов,
   ссылки на артефакты по presigned URL.
5. Присутствие: 🟢/🟡/⚪/🔴 из событий `presence` и состояния задач, без выдуманных статусов.
6. Уведомления: только аппрувы, блокировки, завершение задач; тихие часы.
7. `apps/desktop`: Tauri-обёртка вокруг web, автозапуск, трей, глобальный хоткей.
8. Мобильный вход: подключить канал Telegram в gateway и `bindings` так, чтобы
   DM с ботом в Telegram попадал в ту же сессию, что и тред в ClawDesk.

**Готово, когда:** сообщение боту в Telegram продолжает тред, начатый в десктопе;
аппрув, одобренный в Telegram, разблокирует задачу в вебе (и наоборот).

---

### Задание 4 · Доступы к сервисам

**Что сделать**

1. Поток ручного логина: кнопка «Подключить сервис» → BFF открывает окно браузера
   бота на нужном URL (через CDP бота) → человек входит → BFF фиксирует успешный вход
   (проверка по селектору/URL) → запись `bot_accesses` со статусом `healthy`.
2. Хранилище секретов: SecretRef поверх выбранного бэкенда (локально — зашифрованный
   файл, в VPC — KMS/Vault). API-ключи и токены выдаются рантайму, не модели.
3. Health-check сессий по расписанию: открыть защищённую страницу, проверить признак
   логина; протухло → статус `expired` + карточка «нужен вход» в чат владельца.
4. Детектор капчи/2FA/подозрительной активности: паттерны в DOM и по URL →
   немедленная остановка шага, скриншот, `blocked`, сообщение человеку. Обход запрещён.
5. Правило «API вперёд»: если у сервиса в каталоге коннекторов есть API-метод,
   планировщик рутины обязан предпочесть его UI-шагам.

**Готово, когда:** подключение к тестовому сервису проходит за одно окно логина;
после принудительного удаления cookie бот сам сообщает «нужен повторный вход»;
на странице с капчей бот останавливается и не делает попыток решения.

### Задание 5 · Оркестратор задач и надёжность

**Что сделать**

1. Модель задачи в БД (см. схему в `01-ARCHITECTURE.md`, 5) и машина состояний
   `draft → planned → running → needs_approval → verifying → done | blocked | failed`.
2. Связка с ledger OpenClaw: каждой задаче/подзадаче соответствует запись tasks
   (`oc_task_id`), статусы синхронизируются от событий рантайма, а не опросом.
3. Обязательный контракт бота (реализовать скиллом `clawdesk-core/task-protocol`):
   - перед действиями — план и Definition of Done списком проверяемых утверждений;
   - после выполнения — шаг `verifying`: независимая перепроверка (перечитать запись,
     открыть URL, сверить сумму) с приложением артефакта;
   - при провале — записать причину, изменить подход, максимум 3 попытки;
   - при нехватке данных/прав — `blocked` с одним конкретным вопросом;
   - запрещено отвечать «готово» без артефакта проверки.
4. Декомпозиция: `sessions_spawn` с `context: "isolated"` по умолчанию,
   `fork` — только когда шаг зависит от контекста диалога; ожидание — через
   `sessions_yield`; статусы детей отражаются в родительском треде.
5. Бюджеты: лимит на задачу (токены, деньги, время) и на бота в день;
   исчерпание → `blocked` + уведомление, не тихое завершение.
6. Отмена задачи: корректное закрытие sub-агентов, вкладок браузера и процессов.
7. Ежедневная сводка (cron): сделано / ждёт аппрува / заблокировано / потрачено.

**Готово, когда:** искусственно сломанный шаг (сервис возвращает ошибку) приводит
к трём осмысленно разным попыткам, затем к `blocked` с внятным вопросом;
задача, где бот «сделал вид», что закончил, не может получить `done` без артефакта.

### Задание 6 · Политики и аппрувы

**Что сделать**

1. `packages/policy`: движок правил `(botId, tool, args, context) → allow |
   allow_with_receipt | require_approval(reason, risk) | deny(reason)`.
   Правила — декларативные (JSON), с приоритетами и понятным трейсом решения.
2. Дефолтная политика: платежи, внешние письма и сообщения, удаления, массовые
   изменения (> 20 записей), изменение прав, публикации, покупки, `exec` вне sandbox,
   любые действия в сервисах с меткой `critical`.
3. Плагин `plugins/clawdesk-bridge`: хук на вызов инструмента, который спрашивает
   политику у BFF, при `require_approval` приостанавливает шаг, создаёт Approval
   и ждёт решения (или TTL).
4. Карточка аппрува: намерение, обоснование, риск, дифф/сумма, скриншот, кнопки;
   «Изменить» = отправить боту правку и продолжить с того же места.
5. Правила авто-аппрува с лимитом и сроком (`approval_rules`), создаются из карточки.
6. TTL 24 ч → `blocked`; для `critical` — эскалация второму человеку.
7. Все решения — в неизменяемый аудит с указанием, кто и когда решил.

**Готово, когда:** тест пытается отправить письмо вовне без правила — всегда Approval;
после создания правила «до $100 на 30 дней» платежи ниже лимита проходят,
$150 — снова спрашивают; истёкший TTL оставляет задачу заблокированной, а не выполненной.

### Задание 7 · Обучение рутин

**Что сделать**

1. `packages/routine-spec`: схема `RoutineSpec` (`examples/routine.schema.json`)
   и компилятор `RoutineSpec → SKILL.md` (frontmatter + процедура + критерии приёмки),
   запись в `<workspace>/skills/<routine-id>/SKILL.md`.
2. Обучение текстом: пользователь описывает процедуру → LLM строит `RoutineSpec` →
   мастер уточняет параметры и критерии успеха → пробный прогон.
3. Обучение показом (`plugins/clawdesk-recorder`): расширение/CDP-рекордер пишет
   трассу — URL, роль и стабильные селекторы элементов, вводимый текст с маскированием
   секретов, скриншоты, тайминги. Компилятор превращает трассу в шаги,
   определяет кандидатов в параметры (значения, которые меняются) и точки решения.
4. Гибридное исполнение: устойчивые шаги (навигация, логин, экспорт) — сгенерированный
   Playwright-скрипт; шаги суждения — модель. Признак задаётся в шаге `RoutineSpec`.
5. Обязательный пробный прогон в тестовом режиме с диффом ожидаемого/полученного;
   публикация только после подтверждения человеком (через Skill Workshop).
6. Версионирование рутин и откат; триггеры: manual, cron, webhook (`hooks.*`), watch.
7. Самолечение (P2, заложить точку расширения): шаг не нашёл элемент → поиск по
   текстовому описанию → предложение обновить селектор с уведомлением человеку.

**Готово, когда:** после одной демонстрации выгрузки отчёта бот повторяет процедуру
для другого периода без подсказок в 4 прогонах из 5; рутина ставится на cron
и выполняется в назначенное время; изменение имени кнопки на странице приводит
к внятной ошибке и предложению переобучить шаг, а не к молчаливому провалу.

### Задание 8 · Команда ботов

**Что сделать**

1. Групповые треды: несколько ботов + человек, обращение `@имя`, требование упоминания
   в группах (`requireMention`), общий контекст артефактов треда.
2. Бот-диспетчер (профиль `dispatcher`): разбирает запрос, создаёт подзадачи,
   раздаёт их через `sessions_spawn` / agent-to-agent, синтезирует итог.
3. Включить `tools.agentToAgent` только с явным allowlist пар ботов;
   логировать каждое межботовое сообщение как событие аудита.
4. Защита от петель: максимальная глубина вложенности, квота сообщений между парой
   ботов в единицу времени, детект повторяющихся пар «запрос-ответ» → стоп + аудит.
5. Передача задачи другому боту с полным контекстом и историей.

**Готово, когда:** запрос с тремя `@упоминаниями` порождает три параллельные подзадачи,
результаты приходят push-completion, диспетчер выдаёт один сводный отчёт;
искусственная петля из двух ботов останавливается за ≤ 5 обменов.

---

### Задание 9 · Аудит, стоимость, администрирование

**Что сделать**

1. Событийный аудит: каждый вызов инструмента → `events` с редакцией секретов,
   hash-chain для неизменяемости, скриншоты до/после значимых действий браузера в S3.
2. «Показать работу» и человеко-читаемый отчёт «что делал бот за период».
3. Экспорт аудита JSONL/CSV с фильтрами; настраиваемый ретеншн и автоудаление.
4. Учёт стоимости: usage из gateway → деньги по прайсу провайдера → отображение
   в треде и в отчётах по ботам и рутинам; бюджеты и hard-stop.
5. Failover моделей (`auth.order`), экономный режим: дешёвая модель по умолчанию,
   эскалация на дорогую по правилу.
6. Онбординг-мастер: ключ провайдера → первый бот → первая задача.
   Цель — 20 минут от нуля до результата.
7. Здоровье системы: статус gateway, контейнеров, провайдеров, очередей;
   бэкап/восстановление конфига, workspace, профилей и БД.

**Готово, когда:** в треде видна стоимость каждой задачи; экспорт аудита проходит
проверку «по логу можно восстановить все действия бота за день»; восстановление
из бэкапа на чистой машине возвращает ботов вместе с их логинами.

## 5. Общие критерии приёмки

Итерация считается завершённой, когда демо-сценарий из `02-FUNCTIONALITY.md`
проходит целиком, и при этом:

| Проверка | Требование |
|---|---|
| Изоляция | Два бота — два контейнера, два Chrome-профиля, непересекающиеся куки и секреты |
| Аппрувы | Ни одно необратимое действие не прошло без записи решения человека |
| Надёжность | Нет задач в статусе `done` без артефакта проверки |
| Устойчивость | Перезапуск gateway и BFF не теряет треды, задачи и логины ботов |
| Безопасность | Секреты отсутствуют в транскриптах, логах и аудите (автотест на паттерны) |
| Стоимость | У каждой задачи есть измеренная стоимость; бюджет останавливает перерасход |
| Скорость старта | Чистая машина → первая выполненная задача ≤ 20 минут |
| Апстрим | Ядро OpenClaw не форкнуто; отличия от апстрима — только конфиг, плагины, скиллы |

## 6. Порядок работы

1. Задания 1 → 2 → 3 дают видимый каркас (мессенджер с реальным ботом) — делать строго подряд.
2. Задания 4, 5, 6 — ядро ценности, можно вести параллельно тремя потоками,
   но 6 зависит от 5 в части state machine.
3. Задание 7 стартует после 4 и 5.
4. Задания 8 и 9 — после того как одиночный бот стабильно проходит демо-сценарий.
5. После каждого задания: демонстрация на демо-сценарии, обновление `CHANGELOG.md`,
   PR в ветку проекта, короткая заметка «что стало возможно».
